1. Scoping call

Decide how data will travel from their system to ours, and who owns every dependency, before anyone writes code.

Who does what

  • UsLead the call (Teams, usually recorded). If the client set it up there may be no transcript, so take your own notes. Listen for blockers and signal an effort tier.
  • Our company SupportNot involved yet.
  • ClientShould bring their IT team or ERP partner. If they are not on the call, ask when you can get them.

Exit gate: confirm all of this before you hang up

The question checklist
Source system
  • Which ERP, and which version?
  • Cloud, on-premises or hybrid?
  • Who runs the environment: client IT, an ERP partner, a third party?
Connection and API
  • Is there an API (REST, OData, SOAP)? Reachable over public HTTPS?
  • Which authentication: OAuth2, Basic, API key, session token?
  • Has the client tested it? Can they share a Postman collection or curl?
  • Rate limits, session timeouts, concurrency limits?
Network and firewall
  • Do they need to allow inbound connections from Our company? Who owns that?
  • Any IP ranges we must whitelist on our side?
  • On-prem: VPN or tunnel, or can the API be exposed?
Fallback files
  • If no API: can they deliver a CSV or flat file by SFTP?
  • Format, naming convention and frequency?
Data scope
  • How many companies or entities?
  • How many years of history?
  • Which dimensions, and how many members?
  • FC, FPA or both?
  • Drill Across (transaction detail), or GL balances only?
  • Is budget or forecast in scope?
  • Single currency or multi-currency?
Our company side
  • Instance URL and live product?
  • Is our company's model built, or still in progress?
  • Who is our company's consultant for dimension questions?
Timeline and ownership
  • Go-live date or board meeting driving it?
  • Who owns API config, credentials and firewall rules?
  • How does the client create a read-only integration user?

Watch out

Never paper over a blocker with optimism. If the ERP is new to us, say it is a research item and size it as Premium. Never over-promise on a call.

Self-check

The client says their API is only reachable inside their network. What do you do?

Treat it as a blocker with an owner. Find out who controls the firewall or VPN, whether the API can be exposed, and whether an SFTP file export is a workable alternative. Write it in the open unknowns list.

Which effort tier fits a well-documented ERP API integration?

Enhanced, 40h. Direct SQL or a clean SFTP file is Standard (24h). A new or undocumented ERP is Premium (80h).

3. Postman check (API sources only)

For API sources on a hosted DIS Controller, prove the connection works with real data before you open DI Studio. This is the gate that protects your time.

Who does what

  • UsAPI sources only: build the Postman requests, authentication first, then a data endpoint, then page two.
  • Our company SupportNot involved.
  • ClientFixes access issues when the test fails: permissions, firewall, credentials.

Exit gate (API sources only): Postman returns real data

For SQL and SFTP sources there is no Postman check, so none of this gate applies.

Watch out

If Postman shows a blocker, send the client the exact error straight away. Do not work around it, and do not start the build.

Self-check

The auth works but the data call returns 401. Do you start the DI Studio build?

No. The gate is not met. Send the client the specific error and wait for access to be fixed.

The client's ERP data comes from SQL views or an SFTP file. Do you run a Postman check?

No. The Postman check is only for API sources on a hosted DIS Controller. Skip phase 3 and move on to the build.

Why confirm the date format from the real response?

Each source formats dates differently, and we always normalise them in staging. Assuming a format is how wrong periods reach Our company.

The FC Process pattern for new builds

Every new FC integration is an FC Process with three jobs. DI Studio owns only the middle one.

Job 1: Select PeriodFC-native job
Job 2: Data IntegrationThe DI Studio job, your work
  1. Extract from source
  2. Load into MySQL staging (Recreate)
  3. Staging to the FC agent
Job 3: Import to FCFC-native job
  • Name the period staging table [clientcode]_FC_[ProcessName]_ConsoCode. The old FC_ViewDataConsoCode name is for legacy standalone jobs only.
  • Filter data to the selected period by joining on it: JOIN [clientcode]_FC_[ProcessName]_ConsoCode v ON TRIM(r.Period) = TRIM(v.Period).
  • FPA integrations are configured through the FPA Process Manager import instead.
Set up before you write code
  • A Script Agent connection, with credentials stored as env[] variables on the connection.
  • A MySQL agent connection to the client's staging RDS.
  • A connection for the source, using the agent type that matches it (see the agent list in the toolbox).
  • Check the team's SQL pattern library before writing any transformation. A proven pattern probably exists.
  • Filters (fiscal year, entity, date range) go on the task as query[] parameters.

Watch out

DI Studio only runs whole jobs. To test one step, build a throwaway job containing only that step, or run the SQL directly in MySQL Workbench.

Self-check

A task keeps failing. Can you disable it while you debug the rest?

No. Tasks and steps cannot be disabled. Build a temporary job with just the part you want to test, or run the SQL or script logic outside DI Studio.

Why never rebuild a table (Recreate) and query it in the same step?

Tasks in one step run in parallel, so the read can collide with the rebuild. Put the downstream query in the next step, which only starts when the first finishes.

5. Staging check

Prove the numbers in staging are right before they touch Our company. Fix problems here, where they are cheap.

Who does what

  • UsValidate directly in MySQL and fix anything wrong before loading.
  • Our company SupportNot involved.
  • ClientConfirms unclear mappings and can provide a known number to trace.

Exit gate: staging data is proven correct

Watch out

Validate with actual row-level data before you accept a diagnosis. A plausible theory is not evidence. Trace specific rows through each stage until you find where they change.

Self-check

Some negative amounts show up positive after transformation. Likely cause?

A cleanup step stripped non-numeric characters, including the minus sign. Use a sign-preserving cast, shown in the MySQL section of the toolbox.

Blank source cells turn into 0 in a numeric column. What do you check?

Empty string versus NULL. In MySQL, CAST('' AS UNSIGNED) gives 0. Handle it explicitly with COALESCE(NULLIF(TRIM(...), ''), ...).

  • Our company SupportNot involved.

Exit gate: first load validated

Reading a job log
StatusMeaning
SuccessCompleted without error.
ErrorThis step failed.
CancelledA person cancelled it, or an earlier step failed and this one was skipped.

The first step that is not Success is the real failure. Everything cancelled after it is downstream noise.

Where jobs can be triggered
  • From DI Studio directly: manual runs only.
  • From FC, FPA or FPA+ through Process Manager: manual or scheduled.
  • Exposed task filters work in FPA+ Process Manager only, not in FC.

Watch out

Do not schedule before the first manual run has been validated. A wrong load repeated every night is harder to clean up than a single one.

Self-check

Where do you configure the nightly schedule?

In the Process Manager of our company's product (FC, FPA or FPA+). DI Studio cannot schedule jobs.

The log shows Error on step 2 and Cancelled on steps 3 and 4. Where do you look?

Step 2. Steps 3 and 4 were skipped because of it.

Facts that save you hours

  • Whole jobs only. You cannot run a single step. Build a mini job or run the SQL directly.
  • Nothing can be disabled. No skip toggle exists for tasks or steps.
  • No scheduler. Scheduling happens in Process Manager in our company's product.
  • First failure is the real one. Cancelled items after it are noise.
  • Three kinds of variable. query[] filters live on a task. env[] lives on a connection and is where credentials go. GetKey and SetKey read and write the settings table Our company_Data_Integration_Setting in MySQL.
  • SQL Server destinations need schema write permission, in both Recreate and Append modes.

The Script Agent is where you call APIs, page through results and hand rows to DI Studio. It is most relevant for API sources. One runtime quirk matters more than all the rest: DI Studio uses ClearScript, not Node.js.

Do this
var month = query["Month"];
if (!month) {
    agent.Done(false);
    throw new Error("Month filter is required.");
}

var response = http.Get(url, headers);
if (!response.IsSuccess) {
    agent.Done(false);
    throw new Error("Fetch failed: " + response.StatusCode);
}

agent.Send(JSON.parse(response.GetString()).value);
agent.Log("Page sent.");

agent.Done(true);   // unconditional last line
Never this
try {
    // ...
} catch (err) {
    throw new Error(err.stack);  // undefined in ClearScript
} finally {
    agent.Done(true);            // fires even on failure
}

The rules

  • No try/catch/finally. ClearScript throws strings, so err.stack and err.message are undefined and the real error disappears from the job log.
  • agent.Done(false) right before every throw. It is the only way DI Studio registers a failure.
  • agent.Done(true) as the last line, unconditionally, with no wrapper.
  • Retry only 502, 503 and 504. A 400, 401 or 403 is a real bug and must fail fast.
  • Send per page. Call agent.Send for each page. Never collect millions of rows in memory first.
  • Use http.Get and http.Post. XMLHttpRequest does not exist on the server side and fails silently.

You do not need all of SQL. Six moves cover most of our transformations. Each one is shown next to its Excel equivalent. Before writing any of them from scratch, check the team's SQL pattern library.

1. Filter rows

Excel: AutoFilter.
SELECT *
FROM tbl_client_raw
WHERE Entity = 'E01';

2. Helper columns first (CTE)

Excel: a scratch sheet of helper columns.
Put a Params CTE first so period logic lives in one place.
WITH Params AS (
  SELECT Period AS FullCode,
         LEFT(Period, 4) AS TargetYear,
         CAST(SUBSTRING(Period, 5, 2) AS UNSIGNED) AS TargetMonth
  FROM abc_FC_Actuals_ConsoCode
  LIMIT 1
)
SELECT * FROM Params;

3. Lookups (JOIN)

Excel: VLOOKUP.
Trim both sides, or invisible spaces will break the match.
SELECT r.*, m.TargetAccount
FROM tbl_client_raw r
JOIN tbl_account_map m
  ON UPPER(TRIM(r.Account)) = UPPER(TRIM(m.Account));

4. Totals (GROUP BY)

Excel: a pivot table.
SELECT Entity, Account, SUM(Amount) AS Total
FROM tbl_client_clean
GROUP BY Entity, Account;

5. Safe numbers

Excel: CDbl with error handling.
Keep the minus sign, and treat blanks on purpose.
CASE WHEN Amt REGEXP '^-?[0-9]+([.][0-9]+)?$'
     THEN CAST(Amt AS DECIMAL(18,2))
     ELSE 0 END

COALESCE(NULLIF(TRIM(Amt), ''), '0')

6. Running totals

Excel: =SUM($B$2:B2) filled down.
Needed for balance sheet accounts in FPA. MySQL 8 has window functions. Check the team's SQL pattern library for the proven join version.
SELECT Entity, Account, PeriodNo,
  SUM(Movement) OVER (
    PARTITION BY Entity, Account
    ORDER BY PeriodNo) AS Balance
FROM tbl_client_clean;

One staging trap to know now

Loading in Recreate mode makes every column longtext. If a downstream step expects numbers or dates, add an explicit ALTER TABLE step to cast the columns. The standard pattern is a pure SELECT as the source query, with the target table set to Recreate.

Survival kit

What to keep within reach after the first week.

Ten gotchas that cost the team real hours

  1. try/catch hides errors in scripts. Use agent.Done(false) before each throw and agent.Done(true) as the last line.
  2. Only whole jobs run. To test a step, build a mini job or run the SQL outside DI Studio.
  3. No XMLHttpRequest. Use http.Get and http.Post.
  4. Stripping characters kills negatives. Use sign-preserving casts.
  5. Empty string is not NULL. CAST('' AS UNSIGNED) is 0. Handle blanks explicitly.
  6. Recreate makes everything longtext. Cast columns with ALTER TABLE before using them.
  7. Never Recreate and query the same table in one step. Tasks in a step run in parallel.
  8. Never mix FC and FPA period formats. FC is yyyymmVVV000, FPA is yyyyMmm.
  9. Retry only 502, 503 and 504. A 400 or 401 should fail fast.
  10. Cancelled steps are noise. Find the first step that is not Success.
